## New Round 1: implemented method and actual evidence

### Exact search domain

`assets/js/core/calendar-search.js` exports the criteria catalogue, strict request normalizer, `searchCalendarDates`, `compareSearchStrategies`, `buildEventCalendarSignature`, `analyzeEventCalendarAssociation`, and bounded CSV/JSON event import. A request names an inclusive Gregorian civil-date range, IANA zone, observer, house/prayer conventions and a local sample clock. That clock is resolved afresh on every date with ambiguous and nonexistent clocks rejected and reported. A date-only event is never silently promoted to its real historical timestamp.

Criteria are ANDed; multiple values within one criterion are ORed. Implemented criteria are civil weekday, exact named civil-calendar field text, broad phase/tithi/karaṇa/nakṣatra/yoga index, a named inherited rule class, or a minimum count of one class within one named tradition. Counts do not net favorable and caution rules or combine cultures into a universal score. Every hit includes separate tradition counts, unknown classes, source IDs, rule thresholds and dependency groups. Phase, tithi, karaṇa, waxing and solar proximity reuse Sun/Moon inputs.

The default request permits 366 daily samples. An explicit advanced `maxDays` can allow all 73,414 civil dates from 1900-01-01 through 2100-12-31. The hard limit is the existing engine range, not a promise of instant execution. Returned rows are capped at 1,000, while the complete selected range is visited and total matches/truncation remain visible. The UTC bounds also apply after zone resolution, so a local endpoint can be unavailable. The search is exhaustive only over its declared daily sample grid; it does not solve all continuous-time transitions, inspect every hour or establish whole-day validity.

### Reference versus optimized strategy

The brute reference resolves every clock and evaluates the canonical full comparison and historical guide for every resolved sample. The optimized strategy performs the **same clock/range validation first**, then checks exact civil weekday/calendar fields and necessary lunar-index conditions using the existing `bodyPosition`, `toSidereal` and `nakshatraOf` helpers. It does not skip dates by a coarser sampling grid. Any selected lunar angle within `1e-8` of an integer partition ratio falls through to the full engine; no tolerance snapping changes a canonical boundary. All retained candidates use the full canonical comparison/guide.

Benchmark equivalence compares normalized request, all matched date/UTC identities **including candidates beyond the returned-row cap**, full returned sample rows, counts, missing records and truncation. Candidate identity arrays are bounded by the 73,414-date domain. Timing and work counters are excluded from semantic equality. The same explicit sample and deterministic canonical engine supply the detailed rows; one successful benchmark is not a broad-range mathematical proof or independent ephemeris validation.

Counters name actual work: `canonicalEvaluations` includes the explicit `compareMoment` and the comparison called within `buildDayGuidance`; `guidanceEvaluations` counts guides, not individual historical rules. `civilPrefilters`, `lunarPrefilters`, `lunarBodyEvaluations`, `boundaryFallbacks`, `earlyRejected` and `cacheHits` remain separate. Timings are local run wall time. A 31-day Delhi weekday+tithi trial produced identical candidates with 62 versus 4 canonical evaluations and approximately 409.8 versus 26.8 milliseconds. This measured example is not a speed guarantee.

### Worker and cancellation

`assets/js/workers/calendar-search-worker.js` accepts `{type:'start',jobId,operation,request,mode?}`, where operation is `search`, `benchmark`, `signature` or `association`. It emits job-tagged `progress`, `result`, `error` or `cancelled`. Job IDs are bounded to 80 alphanumeric/underscore/hyphen characters. One operation runs per worker; a second receives `BUSY` rather than replacing the first. `{type:'cancel',jobId}` cooperatively stops the matching job at a yielded checkpoint; the UI can terminate the worker immediately. Cancelled jobs do not publish a success result. The module makes no external request, writes no storage and receives no birth record.

### Event directions and descriptive comparison

Event → calendar: a user-selected date-only event, observer and acknowledged sample clock produce a canonical sample. Only explicitly selected signature fields become suggested search criteria. Selecting features after seeing an event conditions the search on that event; later matches are exploratory, not predictive validation.

Calendar → events: selected criteria are evaluated against an explicit event set and deterministic shifted dates. Default offsets are −28, −14, −7, +7, +14 and +28 civil days; at most 12 unique, nonzero offsets within ±3,660 days are accepted. Each shifted date resolves the same local clock separately. This is a **date-shift comparison**, not independent control subjects, randomization or a permutation-null distribution.

For each selected feature and the joint criterion, event and shifted rows report total, observed, missing, matched and `matched / observed`. The descriptive effect is event proportion minus control proportion. The ratio is unavailable when either denominator is missing or the control frequency is zero, with an explicit `ratioStatus`. Each offset comparison includes only event/control pairs where both selected features are available. Pooled denominators are separately displayed. Unknown opening-portion yoga classifications are missing rather than known negative outcomes. Event-record duplicates and overlapping event/control dates are counted and disclosed; cached calculation reuse is not an independent replication.

There is no p-value, significance test, multiplicity-adjusted discovery, causal inference, historical good/bad event coding or outcome-risk estimate. Weekday-preserving shifts, seasonality, lunar-cycle dependence, historical scheduling, convenience selection, repeated dates and data-selected features limit interpretation. A future rule concurrence means only that the named inherited classes meet the selected count at that sampled instant.

## New Round 3: complete-window ranking and statistical/schema challenge

Added an explicit `order:'concurrence'` option; the default remains `chronological`. Count ordering requires a chosen tradition, favorable/caution class and minimum. Every sampled candidate is still considered. A binary insertion retains at most `maxResults` detailed rows, ordered by the **known chosen-rule count descending**, then civil date ascending. It does not sort only the first returned page, store every full matching row or combine traditions into a net score. The equivalence benchmark still compares every matched date/UTC identity, including unreturned matches.

Each ranked row exposes `position`, `traditionId`, `classification`, `knownCount`, `totalRules`, `availableRules`, `unavailableRules`, `completeForChosenTradition` and an explicit scope note. Missing classes are not assigned zero; their count and the incompleteness flag remain visible. A count can meet a minimum while the remaining classes are unknown. Completeness of the chosen tradition also differs from `fullyObserved` across all selected criteria: a polar unavailable-hour criterion can coexist with a complete Western count. No rank is presented as a scientifically best/worst day, continuous-time maximum or outcome forecast.

Executed example: in the October 2026 Delhi trial, the first chronological match on 1 October has two favorable Western rules. The complete-window count order instead retains 23 October with three known favorable rules, even with a small return cap. Both strategies preserve all 30 matching identities.
